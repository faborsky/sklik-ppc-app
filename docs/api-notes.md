# Sklik DRAK API — behaviour notes & gotchas

The single reference for how the DRAK JSON API actually behaves (verified against
the official docs at https://api.sklik.cz/drak/). CLAUDE.md links here; keep the
deep detail in this file and the signpost lean.

## API Notes

- **Endpoint pinned to v5**: `https://api.sklik.cz/drak/json/v5` (not the unpinned `.../drak/json`, which silently follows the newest version and could break on a major bump).
- Protocol: JSON-RPC POST to `https://api.sklik.cz/drak/json/v5/{method}`
- Params sent as JSON array: `[userStruct, ...params]`
- Reports are two-step: `createReport` (dates in restriction) → `readReport` (pagination + columns)
- **Money units in report stats are INCONSISTENT**: `totalMoney`, `clickMoney`, `impressionMoney`, `avgCpc` come back in **haléře**, but **`conversionValue` is plain CZK** (it's the value the conversion code sends). Verified live (2026-07-20) against the API's own `pno` column: `pno` (a percentage) equals `totalMoney/100 ÷ conversionValue × 100` — consistent only with conversionValue in CZK. Mind the contrast with conversion *definitions* (`conversions.list` field `value`), which ARE in haléře. `conversionPrice` is not a real report column (`readReport` rejects it). CLI ≤ 1.7.1 wrongly divided `conversionValue` by 100 → 100× understated value in all `*-stats`/`search-queries` JSON and 100× overstated PNO in `pulse`; fixed in 1.7.2 (found by a user report).
- Campaign budget is nested as `budget.dayBudget` in list responses but flat `dayBudget` in create
- **Ad text updates (`ad-replace`, NOT manual remove+create)**: `ads.update` cannot edit an existing ad's text — per the docs *"Ad title, content and URLs cannot be changed. Old ad will be deleted and new one will be created and newIds will be provided in response."* This delete-old + create-new happens as **ONE atomic server-side operation**, so a validation failure (e.g. `ad_duplicate_in_db`) leaves the **original ad intact**. This is why `ad-replace` (which drives `ads.update`) is safe and a manual `ad-remove` + `ad-create` is NOT — the manual pattern's failed create runs *after* the remove, silently dropping the ad (this actually happened in production). `ad-replace` fetches the current ad, applies only the passed fields (so it resubmits the full creative), pre-validates with `ads.check` (`checkDuplicity:false` — the new copy would otherwise self-match the ad being replaced), then does the atomic swap. Text/eta ads only; combined/banner "replace" = create-first then remove.
- **`ads.check`** = non-mutating dry-run validating a creative before create/update; returns diagnostics (`ad_duplicate_in_db`, length/char/image errors). Options `{checkDuplicity, checkRules, checkRequired}`. Status 406 = creative rejected.
- Keyword `name` and `matchType` cannot be updated — must remove and recreate
- **Filtering**: API does NOT support parent-entity filters (`campaign.ids`, `group.ids`, `status`) in `restrictionFilter`. Only `ids` (own entity IDs), `isDeleted`, and `dateFrom`/`dateTo` (for reports) work. All `--campaign-id`, `--group-id`, `--status` filters are applied client-side.
- **Diagnostics**: Can be a dict `{"operation": {...}, "problems": [...]}` or a list of dicts — handle both formats
- **Error output**: on failure the CLI exits non-zero and, in `--json` mode, prints a parseable `{"error": {"method","status","message","diagnostics":[…]}}` to **stdout** (human-readable text on stderr otherwise) — so an orchestrating caller always gets the real Sklik diagnostic (e.g. `ad_duplicate_in_db`) instead of it being buried in stderr. The macOS `urllib3` LibreSSL/OpenSSL `NotOpenSSLWarning` is suppressed at import so it can't corrupt stdout JSON.
- **Ad rotation (`adSelection`)** on campaign objects: `weighted` (higher CTR, default) / `random` (even split) / `cpa` (lower CPA) / `cos` (lower CTR). Settable via `campaigns.create`/`update` (`--ad-selection`). Use `random` for a clean creative A/B test.
- **Frequency cap (`maxUserDailyImpression`)** on group objects — max impressions per user per day. Settable via `groups.create`/`update` (`--max-daily-impression`). Note the read column in `groups.list` is the plural `maxUserDailyImpressions`; the setter field is singular.
- **Frequency cap exists on BOTH campaign and group — but the API only exposes the GROUP one.** The web UI lets you set "Frekvence zobrazení" on a campaign too; that value has no column in `campaigns.list` nor in the campaign report whitelist, so it is **invisible to the API** and cannot be read or written through it. The **group cap wins** where both are set: a campaign changed to 3/day while its group stayed at 2/day kept serving 2 (verified live 2026-08-11 — the change produced no measurable effect and `groups.list` still reported `maxUserDailyImpressions: 2`). When automating, treat the group cap as the effective one and don't trust a campaign-level change to take effect.
- **Stat columns are NOT the same for every report entity.** Asking for a column an entity doesn't support fails the whole `readReport` with `400 Bad arguments`, so they can't be requested blindly. Verified live 2026-08-11 by sending an invalid column and reading the whitelist the API returns in the error message — a cheap way to enumerate what any entity accepts:
  - **`winRate`** (share of auctions won, returned as a 0–1 fraction) — **groups only**. Campaigns, keywords and ads have no equivalent; `ish`/`ishSum`/`ishContext` are a different (and on display campaigns constant, uninformative) metric.
  - `avgCpt` — campaigns, groups, ads (**not** keywords).
  - `exhaustedBudgetShare`, `underForestThreshold`, `stoppedBySchedule` — campaigns, groups, keywords, ads (**not** queries).
  - `impressionMoney`, `clickMoney` — everywhere including queries.
  - `adSelection` — campaigns only (readable via `campaigns.list`, not just writable).
  Wrapped since v1.8.0 as `stat_columns(entity)` in `sklik/reports.py`.
- **Report ratios are fractions, not percentages.** `ctr`, `winRate` and `exhaustedBudgetShare` come back as 0–1 (a 0.73 % CTR arrives as `0.0073`). The `--json` output passes them through unchanged; only the human-readable output multiplies by 100.
- **`statGranularity`** in `displayOptions` accepts `total` (default), `daily`, `weekly`, `monthly`, `quarterly`, `yearly` — exposed as `--granularity` on the stats commands since v1.8.0. Every stats row carries a `date`, but on `total` it is just the window's first day while the numbers are the whole-window aggregate — don't read it as a single day.
- **Negative keywords**: Group-level via `keywords.negative.create` (requires `groupId`). Campaign-level via `campaigns.update` with `negativeKeywords` array (requires `type` field). CLI handles both via `--group-id` or `--campaign-id`. **Campaign-level negatives are write-only**: `keywords.negative.list` returns group-level only and `campaigns.list` has no `negativeKeywords` display column (verified live 2026-07-18) — verify them in the web UI. `negatives --campaign-id` therefore filters group-level negatives via the campaign's groups.
- **campaigns.update quirk**: `type` field is ALWAYS required in the update payload (for any field change, not just negativeKeywords). CLI auto-fetches it before updating.
- **Targeting fields** (on campaign objects): `regions` (array of `{id,name}`), `devicesPriceRatio` (`{desktop,mobile,tablet,other}` as % modifiers), `schedule` (`{daySchedule:[{value:[24 hourly 0-100]}, …×7]}`, week starts Monday). Settable via `campaigns.create`/`update`.
- **Conversions**: `conversions.list` takes ONLY the user struct (no restriction/displayColumns). Value in haléře (unlike the report stat column `conversionValue`, which is plain CZK). **SEM caveat**: accounts with Seznam Event Measurement activated cannot use `conversions.*` — CLI prints a friendly hint instead of crashing. `listConversionTypes` is currently broken server-side (HTTP 500), so `conversion-types` derives types from existing conversions instead.
- **Retargeting**: list objects use `listId` (not `id`); create/update nest editable fields under `attributes` (`name`, `membership`, `useHistoricData`, `takeAllUsers`, `description`). `retargeting.lists.list` takes only the user struct.
- **Audience↔group attachment lives in `retargeting.group.lists.*`, not on `groups.*`** (no `retargeting` field there): `add`/`remove` take `[{listId, groupId}, …]`, `list` takes a plain `groupIds` array and returns `{listId, groupId, name, status, deleted}` per attachment (verified live 2026-07-18). Wrapped since v1.6.0 as `retargeting-attach`/`retargeting-detach`/`retargeting-attached`. **Attaching a deleted list → bare `406 Bad values` with no diagnostics** — check `deleted` in the lists output first. **Negative retargeting** (`retargeting.campaign.negative.*` / `retargeting.group.negative.*`) takes `items: [{entityId, campaignId|groupId}]` (`entityId` = list or combination ID) and its report is a date-less listing with `id`/`name`/parent columns — wrapped as `retargeting-exclude`/`retargeting-exclude-remove`/`retargeting-excluded` (verified live 2026-07-19; works on search campaigns too). Still unwrapped: `retargeting.group.combinations.*`, `retargeting.lookalikes.*`, `retargeting.emails.*`.
- **Display targeting dimensions (`interests.*`, `themes.*`, `intends.*`)** attach to GROUPS: create takes `[{groupId, <interestCategoryId|categoryId|intendCategoryId>, cpc?, cpt?, status?}]` (haléře), remove/restore take plain id arrays. Wrapped as the unified `targeting*` commands (`--type interest/theme/intend`). Quirks (verified live): reports have **no `name` column** — only `categoryId` (CLI joins names from the catalog); **removal is soft** — re-creating the same category → `409 entity_already_exists`, use `.restore` (CLI: `targeting-restore`); negative reports take **no dates** in restrictionFilter (plain listing).
- **`patterns.negative.*` (excluded placements)**: create takes `[{groupId, pattern}]`; report is a **date-less listing** and — server quirk — **never returns the `pattern` column value**, so the excluded URL text is API-invisible (web UI only). Removed exclusions block re-creating the same pattern (`group_pattern_duplicity`) → use `patterns.negative.restore` (CLI: `placement-exclude-restore`).
- **`sitelinks.campaign.set` / `sitelinks.group.set` REPLACE the whole assignment** of the campaign/group (empty `sitelinkIds` clears it); `sitelinks.update` requires `name` in every payload (CLI merges current values) and **renaming creates a new sitelink ID** (server remove+create; response `ids` carries the new one). `sitelinks.list` returns soft-deleted rows (`deleted: true`) — CLI filters them.
- **`sharedbudgets.*` amounts are plain CZK** (create `dayBudget` int Kč, list returns double Kč) — like `client.getCredit` and the report column `conversionValue`, one of the few places WITHOUT haléře. Campaign assignment is managed on the budget (`addCids`/`removeCids`/`removeAllCids` in update), not via `campaigns.update`.
- **`stats.status`** takes `[{dateFrom, dateTo}]` (YYYY-MM-DD), returns per-day `preparing`/`complete`/`error` (dates come back as `20260718T0…`). `pulse` calls it softly and warns when the window isn't complete. **`client.getCredit`** takes no params and returns all managed users' credit in plain CZK. **`listPredefinedRegions`** (no `campaigns.` prefix) returns `{id, name}` region catalog. **`autotagging.get`** returns read-only fields (`separatorChar`) that `autotagging.update` rejects — whitelist before writing back (CLI does).
- **Banners**: `banners.create` takes the image bytes directly in `file` (base64 over JSON) — NOT an image-id; CLI base64-encodes a local path or downloads a URL. Required fields: `groupId`, `name`, `clickthruUrl`, `file`. List/return quirks: list columns use `bannerName`/`adStatus` (not `name`/`status`); `banners.create` returns `bannerIds` as `[{"id":…,"requestId":…}]` (CLI normalises to ints). Allowed formats via `images.constraints.list` (fixed sizes, ≤250 KB). The separate `images.*` namespace (URL + metadata, Sklik downloads) is NOT used. **Downloading creatives**: `banner-download` reads the `image.url` column via `banners.list` (the old `imageURL` column is deprecated and always returns an empty string) and saves the files locally — the Sklik UI has no bulk creative export.
- **Combined (native) ads**: created via `ads.create` with `adType: combined`. Both `image` (landscape 1.91:1) and `imageSquare` (1:1) are REQUIRED; binary data is base64-encoded inline (same as banners), or pass `imageId`/`imageSquareId` referencing the `images.*` namespace (CLI uses inline data only). Optional `imageLogo` (1:1) / `imageLandscapeLogo` (4:1) — Sklik shows at most one logo, display not guaranteed. Colors (`colorMain`, `colorAccent`) are hex WITHOUT the leading `#` (CLI strips it). **Sklik silently strips forbidden characters from texts** (e.g. em dash "—" in `longLine`) — no warning, no error; verify final wording via `ads.list`. Combined fields (`shortLine`, `longLine`, `companyName`) are valid `ads.list` displayColumns and come back `null` for other ad types.
- **Placements (patterns)**: `patterns.create` takes `[{groupId, pattern, cpc?, cpt?, status?}]`; returns `ids`. `pattern` = plain domain or URL path string (no wildcards needed: `"forbes.cz"`, `"www.e15.cz/byznys"`). There is NO `patterns.list` (404) — list via `patterns.createReport` + `readReport` with displayColumns `["id","pattern","status","cpc","group.id","group.name"]`. Negative placements = `patterns.negative.*` (not wrapped in CLI).
- **Rate limits & item caps**: not fixed in the docs — they're account-specific and queryable at runtime via the `api.limits` method, which returns `minuteRequestLimit`, `dayRequestLimit`, `statsDataLimit`, and `batchCallLimits[]` (per-method `{name, limit}` = max items per batch call), plus value ranges (`CpcMin/Max`, `CpmMin/Max`, `dayBudgetMin/Max` in haléře), `bannerSizeKBMax`, `retargetingMembershipDurationMax`, and `valueAddedTax`. Exposed via the `api-limits` command (also shows live local usage).
- **Local request budget (cross-session)**: `_api_call` tracks every request's timestamp in a per-account file `.rate_limit_<account>.json` (sibling to the session cache, git-ignored) and checks it BEFORE each call — so the budget is respected even across separate CLI runs and parallel sessions. Limits come from `api.limits` (cached ~1×/day); the CLI throttles at `RATE_LIMIT_SAFETY` (90%) of the stated values. **Minute ceiling → waits out the rolling 60 s window then proceeds** (capped at `RATE_LIMIT_MAX_WAIT`=180 s). **Day ceiling → hard stop (`sys.exit(1)`), never loops** — a runaway job can't keep hammering an account already at its daily limit. If `api.limits` can't be fetched, conservative fallbacks apply (`RATE_LIMIT_FALLBACK_MINUTE/DAY`). This is the primary defence against the real risk that excessive API traffic gets a (high-spend) account throttled or blocked — it does NOT depend on the model remembering to behave.
- **Throttling status `429`** ("Too many requests. Has to wait."): the local budget should prevent this, but if Sklik still returns 429 (e.g. other tools sharing the same login), `_api_call` retries with linear back-off (5 s, 10 s, 15 s) and **gives up after 3 retries** (`sys.exit(1)`) — no infinite loop.
- **Overflow status `413`** ("Too many items requested."): returned when a batch call exceeds that method's `batchCallLimits` entry (check via `api-limits`). NOT specially handled — surfaces as a generic error and exits; there is no client-side chunking, so split large `keyword-create-batch` / `negative-add-batch` payloads yourself (typically ≤100 items for create/update/remove; report/list allow up to 5000).
- **Recommended account entity caps** (Sklik docs — exceeding causes account slowdown and can break bulk ops/imports/API): ≤250 campaigns, ≤250k keywords, ≤4000 negatives per group, ≤100 ads per group, ≤1000 groups per campaign, ≤1000 targeting entries per group. Batch ops are **all-or-nothing** (any item fails → whole batch rolled back). The API's `*.check` methods validate payloads cheaply; the CLI uses `ads.check` internally in `ad-replace` but doesn't expose check commands.
- **Other status codes** (returned by any method): `200` OK, `206` partial OK (warnings in `diagnostics`), `301` user is serviced, `400` bad arguments, `401` invalid session (CLI re-auths once), `403` access denied, `404` not found, `406` bad attribute values, `409` conflict, `500` server error.
