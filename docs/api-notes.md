# Sklik DRAK API — behaviour notes & gotchas

The single reference for how the DRAK JSON API actually behaves (verified against
the official docs at https://api.sklik.cz/drak/). CLAUDE.md links here; keep the
deep detail in this file and the signpost lean.

## API Notes

- **Endpoint pinned to v5**: `https://api.sklik.cz/drak/json/v5` (not the unpinned `.../drak/json`, which silently follows the newest version and could break on a major bump).
- Protocol: JSON-RPC POST to `https://api.sklik.cz/drak/json/v5/{method}`
- Params sent as JSON array: `[userStruct, ...params]`
- Reports are two-step: `createReport` (dates in restriction) → `readReport` (pagination + columns)
- **Money units in report stats are INCONSISTENT**: `totalMoney`, `clickMoney`, `impressionMoney`, `avgCpc` come back in **haléře**, but **`conversionValue` is plain CZK** (it's the value the conversion code sends). Verified live (2026-07-20) against the API's own `pno` column: `pno` (a percentage) equals `totalMoney/100 ÷ conversionValue × 100` — consistent only with conversionValue in CZK. Mind the contrast with conversion *definitions* (`conversions.list` field `value`), which ARE in haléře. `conversionPrice` is not a real report column (`readReport` rejects it). CLI ≤ 1.7.1 wrongly divided `conversionValue` by 100 → 100× understated value in all `*-stats`/`search-queries` JSON and 100× overstated PNO in `pulse`; fixed in 1.7.2 (found by a user report).
- Campaign budget is nested as `budget.dayBudget` in list responses but flat `dayBudget` in create
- **Ad text updates (`ad-replace`, NOT manual remove+create)**: `ads.update` cannot edit an existing ad's text — per the docs *"Ad title, content and URLs cannot be changed. Old ad will be deleted and new one will be created and newIds will be provided in response."* This delete-old + create-new happens as **ONE atomic server-side operation**, so a validation failure (e.g. `ad_duplicate_in_db`) leaves the **original ad intact**. This is why `ad-replace` (which drives `ads.update`) is safe and a manual `ad-remove` + `ad-create` is NOT — the manual pattern's failed create runs *after* the remove, silently dropping the ad (this actually happened in production). `ad-replace` fetches the current ad, applies only the passed fields (so it resubmits the full creative), pre-validates with `ads.check` (`checkDuplicity:false` — the new copy would otherwise self-match the ad being replaced), then does the atomic swap. Text/eta ads only; combined/banner "replace" = create-first then remove.
- **`ads.check`** = non-mutating dry-run validating a creative before create/update; returns diagnostics (`ad_duplicate_in_db`, length/char/image errors). Options `{checkDuplicity, checkRules, checkRequired}`. Status 406 = creative rejected.
- Keyword `name` and `matchType` cannot be updated — must remove and recreate
- **Filtering**: API does NOT support parent-entity filters (`campaign.ids`, `group.ids`, `status`) in `restrictionFilter`. Only `ids` (own entity IDs), `isDeleted`, and `dateFrom`/`dateTo` (for reports) work. All `--campaign-id`, `--group-id`, `--status` filters are applied client-side.
- **Diagnostics**: Can be a dict `{"operation": {...}, "problems": [...]}` or a list of dicts — handle both formats
- **Error output**: on failure the CLI exits non-zero and, in `--json` mode, prints a parseable `{"error": {"method","status","message","diagnostics":[…]}}` to **stdout** (human-readable text on stderr otherwise) — so an orchestrating caller always gets the real Sklik diagnostic (e.g. `ad_duplicate_in_db`) instead of it being buried in stderr. The macOS `urllib3` LibreSSL/OpenSSL `NotOpenSSLWarning` is suppressed at import so it can't corrupt stdout JSON.
- **Ad rotation (`adSelection`)** on campaign objects: `weighted` (higher CTR, default) / `random` (even split) / `cpa` (lower CPA) / `cos` (lower CTR). Settable via `campaigns.create`/`update` (`--ad-selection`). Use `random` for a clean creative A/B test.
- **Frequency cap (`maxUserDailyImpression`)** on group objects — max impressions per user per day. Settable via `groups.create`/`update` (`--max-daily-impression`). Note the read column in `groups.list` is the plural `maxUserDailyImpressions`; the setter field is singular.
- **Frequency cap exists on BOTH campaign and group — but the API only exposes the GROUP one.** The web UI lets you set "Frekvence zobrazení" on a campaign too; that value has no column in `campaigns.list` nor in the campaign report whitelist, so it is **invisible to the API** and cannot be read or written through it. The **group cap wins** where both are set: a campaign changed to 3/day while its group stayed at 2/day kept serving 2 (verified live 2026-08-11 — the change produced no measurable effect and `groups.list` still reported `maxUserDailyImpressions: 2`). When automating, treat the group cap as the effective one and don't trust a campaign-level change to take effect.
- **Stat columns are NOT the same for every report entity.** Asking for a column an entity doesn't support fails the whole `readReport` with `400 Bad arguments`, so they can't be requested blindly. Verified live 2026-08-11 by sending an invalid column and reading the whitelist the API returns in the error message — a cheap way to enumerate what any entity accepts:
  - **`winRate`** (share of auctions won, returned as a 0–1 fraction) — **groups only**. Campaigns, keywords and ads have no equivalent; `ish`/`ishSum`/`ishContext` are a different (and on display campaigns constant, uninformative) metric.
  - `avgCpt` — campaigns, groups, ads (**not** keywords).
  - `exhaustedBudgetShare`, `underForestThreshold`, `stoppedBySchedule` — campaigns, groups, keywords, ads (**not** queries).
  - `impressionMoney`, `clickMoney` — everywhere including queries.
  - `adSelection` — campaigns only (readable via `campaigns.list`, not just writable).
  Wrapped since v1.8.0 as `stat_columns(entity)` in `sklik/reports.py`.
- **Report ratios are fractions, not percentages.** `ctr`, `winRate` and `exhaustedBudgetShare` come back as 0–1 (a 0.73 % CTR arrives as `0.0073`). The `--json` output passes them through unchanged; only the human-readable output multiplies by 100.
- **`statGranularity`** in `displayOptions` accepts `total` (default), `daily`, `weekly`, `monthly`, `quarterly`, `yearly` — exposed as `--granularity` on the stats commands since v1.8.0. Every stats row carries a `date`, but on `total` it is just the window's first day while the numbers are the whole-window aggregate — don't read it as a single day.
- **Negative keywords**: Group-level via `keywords.negative.create` (requires `groupId`). Campaign-level via `campaigns.update` with `negativeKeywords` array (requires `type` field). CLI handles both via `--group-id` or `--campaign-id`. **Campaign-level negatives are write-only**: `keywords.negative.list` returns group-level only and `campaigns.list` has no `negativeKeywords` display column (verified live 2026-07-18) — verify them in the web UI. `negatives --campaign-id` therefore filters group-level negatives via the campaign's groups.
- **campaigns.update quirk**: `type` field is ALWAYS required in the update payload (for any field change, not just negativeKeywords). CLI auto-fetches it before updating.
- **Targeting fields on campaigns — the write shape differs from the read shape** (all three verified live 2026-08-20 via `campaigns.check` + a real create/update; getting them wrong is a hard 400):
  - **`regions`** — write: `[{"predefinedId": 100001}, …]`; read (`regions.id`/`regions.name` columns): `[{"id":…,"name":…}]`. Bare ints → `400 Parameter campaigns[0].regions[0] must be struct, not int`. Writing **replaces the whole set**, and geo targeting **cannot be cleared via the API** — both `[]` (`400 Array cannot be empty`) and `nil` (`400 … regions cannot be nil`) are refused; only the web UI can remove it.
  - **`devicesPriceRatio`** — `{desktop,mobile,tablet,other}` as whole-percent modifiers, **ints only**; floats → `400 … devicesPriceRatio.desktop must be int, not double` (reads come back as doubles, e.g. `-30.0`).
  - **`schedule`** — write: an array of **7 arrays × 24 hourly ints 0-100** (`[[0,…,100,…], …×7]`, week starts Monday), or `nil` to clear. Read: `{"daySchedule":[{"value":[…24]}, …×7]}` when set, but a plain `[]` when unset. Writing the read shape → `400 … schedule must be array or nil, not struct`; a short week → `406 campaign_invalid_schedule_size`. The CLI accepts both shapes on `--schedule-json` and normalises.
  Settable via `campaigns.create`/`update` (schedule via update). **`campaigns.check` validates any of this for free** — same payload as create/update (with `id` = check an update), no writes, one request.
- **Conversions**: `conversions.list` takes ONLY the user struct (no restriction/displayColumns). Value in haléře (unlike the report stat column `conversionValue`, which is plain CZK). **SEM caveat**: accounts with Seznam Event Measurement activated cannot use `conversions.*` — CLI prints a friendly hint instead of crashing. `listConversionTypes` is currently broken server-side (HTTP 500), so `conversion-types` derives types from existing conversions instead.
- **Retargeting**: list objects use `listId` (not `id`); create/update nest editable fields under `attributes` (`name`, `membership`, `useHistoricData`, `takeAllUsers`, `description`). `retargeting.lists.list` takes only the user struct. URL conditions live in a sibling `conditionGroups` array (NOT under `attributes`): `[{"conditions":[{"type":"contains","value":"/dekujeme"}]}, …]`, `type` ∈ contains/not_contains/equals/not_equals/starts/not_starts/ends/not_ends — exposed as `--conditions-json` (shape verified live 2026-08-20).
- **Audience↔group attachment lives in `retargeting.group.lists.*`, not on `groups.*`** (no `retargeting` field there): `add`/`remove` take `[{listId, groupId}, …]`, `list` takes a plain `groupIds` array and returns `{listId, groupId, name, status, deleted}` per attachment (verified live 2026-07-18). Wrapped since v1.6.0 as `retargeting-attach`/`retargeting-detach`/`retargeting-attached`. **Attaching a deleted list → bare `406 Bad values` with no diagnostics** — check `deleted` in the lists output first. **Negative retargeting** (`retargeting.campaign.negative.*` / `retargeting.group.negative.*`) takes `items: [{entityId, campaignId|groupId}]` (`entityId` = list or combination ID) and its report is a date-less listing with `id`/`name`/parent columns — wrapped as `retargeting-exclude`/`retargeting-exclude-remove`/`retargeting-excluded` (verified live 2026-07-19; works on search campaigns too). Still unwrapped: `retargeting.group.combinations.*`, `retargeting.lookalikes.*`, `retargeting.emails.*`.
- **Display targeting dimensions (`interests.*`, `themes.*`, `intends.*`)** attach to GROUPS: create takes `[{groupId, <interestCategoryId|categoryId|intendCategoryId>, cpc?, cpt?, status?}]` (haléře), remove/restore take plain id arrays. Wrapped as the unified `targeting*` commands (`--type interest/theme/intend`). Quirks (verified live): reports have **no `name` column** — only `categoryId` (CLI joins names from the catalog); **removal is soft** — re-creating the same category → `409 entity_already_exists`, use `.restore` (CLI: `targeting-restore`); negative reports take **no dates** in restrictionFilter (plain listing).
- **`patterns.negative.*` (excluded placements)**: create takes `[{groupId, pattern}]`; report is a **date-less listing** and — server quirk — **never returns the `pattern` column value**, so the excluded URL text is API-invisible (web UI only). Removed exclusions block re-creating the same pattern (`group_pattern_duplicity`) → use `patterns.negative.restore` (CLI: `placement-exclude-restore`).
- **`sitelinks.campaign.set` / `sitelinks.group.set` REPLACE the whole assignment** of the campaign/group (empty `sitelinkIds` clears it); `sitelinks.update` requires `name` in every payload (CLI merges current values) and **renaming creates a new sitelink ID** (server remove+create; response `ids` carries the new one). `sitelinks.list` returns soft-deleted rows (`deleted: true`) — CLI filters them.
- **`sharedbudgets.*` amounts are plain CZK** (create `dayBudget` int Kč, list returns double Kč) — like `client.getCredit` and the report column `conversionValue`, one of the few places WITHOUT haléře. Campaign assignment is managed on the budget (`addCids`/`removeCids`/`removeAllCids` in update), not via `campaigns.update`.
- **`stats.status`** takes `[{dateFrom, dateTo}]` (YYYY-MM-DD), returns per-day `preparing`/`complete`/`error` (dates come back as `20260718T0…`). `pulse` calls it softly and warns when the window isn't complete. **`client.getCredit`** takes no params and returns all managed users' credit in plain CZK. **`listPredefinedRegions`** (no `campaigns.` prefix) returns `{id, name}` region catalog. **`autotagging.get`** returns read-only fields (`separatorChar`) that `autotagging.update` rejects — whitelist before writing back (CLI does).
- **Banners**: `banners.create` takes the image bytes directly in `file` (base64 over JSON) — NOT an image-id; CLI base64-encodes a local path or downloads a URL. Required fields: `groupId`, `name`, `clickthruUrl`, `file`. List/return quirks: list columns use `bannerName`/`adStatus` (not `name`/`status`); `banners.create` returns `bannerIds` as `[{"id":…,"requestId":…}]` (CLI normalises to ints). Allowed formats via `images.constraints.list` (fixed sizes, ≤250 KB). The separate `images.*` namespace (URL + metadata, Sklik downloads) is NOT used. **Downloading creatives**: `banner-download` reads the `image.url` column via `banners.list` (the old `imageURL` column is deprecated and always returns an empty string) and saves the files locally — the Sklik UI has no bulk creative export.
- **Combined (native) ads**: created via `ads.create` with `adType: combined`. Both `image` (landscape 1.91:1) and `imageSquare` (1:1) are REQUIRED; binary data is base64-encoded inline (same as banners), or pass `imageId`/`imageSquareId` referencing the `images.*` namespace (CLI uses inline data only). Optional `imageLogo` (1:1) / `imageLandscapeLogo` (4:1) — Sklik shows at most one logo, display not guaranteed. Colors (`colorMain`, `colorAccent`) are hex WITHOUT the leading `#` (CLI strips it). **Sklik silently strips forbidden characters from texts** (e.g. em dash "—" in `longLine`) — no warning, no error; verify final wording via `ads.list`. Combined fields (`shortLine`, `longLine`, `companyName`) are valid `ads.list` displayColumns and come back `null` for other ad types.
- **Placements (patterns)**: `patterns.create` takes `[{groupId, pattern, cpc?, cpt?, status?}]`; returns `ids`. `pattern` = plain domain or URL path string (no wildcards needed: `"forbes.cz"`, `"www.e15.cz/byznys"`). There is NO `patterns.list` (404) — list via `patterns.createReport` + `readReport` with displayColumns `["id","pattern","status","cpc","group.id","group.name"]`. Negative placements = `patterns.negative.*` (not wrapped in CLI).
- **Rate limits & item caps**: not fixed in the docs — they're account-specific and queryable at runtime via the `api.limits` method, which returns `minuteRequestLimit`, `dayRequestLimit`, `statsDataLimit`, and `batchCallLimits[]` (per-method `{name, limit}` = max items per batch call), plus value ranges (`CpcMin/Max`, `CpmMin/Max`, `dayBudgetMin/Max` in haléře), `bannerSizeKBMax`, `retargetingMembershipDurationMax`, and `valueAddedTax`. Exposed via the `api-limits` command (also shows live local usage).
- **Local request budget (cross-session)**: `_api_call` tracks every request's timestamp in a per-account file `.rate_limit_<account>.json` (sibling to the session cache, git-ignored) and checks it BEFORE each call — so the budget is respected even across separate CLI runs and parallel sessions. Limits come from `api.limits` (cached ~1×/day); the CLI throttles at `RATE_LIMIT_SAFETY` (90%) of the stated values. **Minute ceiling → waits out the rolling 60 s window then proceeds** (capped at `RATE_LIMIT_MAX_WAIT`=180 s). **Day ceiling → hard stop (`sys.exit(1)`), never loops** — a runaway job can't keep hammering an account already at its daily limit. If `api.limits` can't be fetched, conservative fallbacks apply (`RATE_LIMIT_FALLBACK_MINUTE/DAY`). This is the primary defence against the real risk that excessive API traffic gets a (high-spend) account throttled or blocked — it does NOT depend on the model remembering to behave.
- **Throttling status `429`** ("Too many requests. Has to wait."): the local budget should prevent this, but if Sklik still returns 429 (e.g. other tools sharing the same login), `_api_call` retries with linear back-off (5 s, 10 s, 15 s) and **gives up after 3 retries** (`sys.exit(1)`) — no infinite loop.
- **Paging of `*.list` (and `readReport`) — the API never tells you it truncated.** `displayOptions` takes `limit`/`offset`, the response carries **no total count**, and a single call just returns the first page. Asking for more than the account's `statsDataLimit` (5000) fails with `406 You are requiring too much data in one request. Your limit is 5000 and you are requiring N entities`. So the only correct read is to **walk offsets until a short page comes back** — offsets are stable and non-overlapping (verified live 2026-08-20). Since v1.9.0 the CLI does this centrally in `api._fetch_all()` (list methods) and `reports._read_report_rows()` (report reads, where `createReport` DOES return `totalCount` to page against); page size comes from `statsDataLimit` via `api.limits`. **In `readReport`, `offset`/`limit`/`totalCount` count ENTITIES, not returned rows** — identical on the entity reports, but the **`queries` report returns every search query of the keywords in the page**, so asking for 5 keywords can hand back 6 rows and 138 keywords yield 127 query rows (verified live 2026-08-20). Paging must therefore advance the offset by the page size, never by `len(rows)` — that re-reads and duplicates. Side effect: on a report bigger than one page the query rows come back grouped per keyword page, so their ORDER differs from a single-page read (the set is identical). **These methods take no paging params at all** and return everything in one call: `conversions.list`, `sitelinks.list`, `retargeting.lists.list`, `sharedbudgets.list`, `images.constraints.list`, `sitelinks.campaign/group.list`, `retargeting.group.lists.list` (that one takes the group IDs as one array instead — the CLI chunks it).
- **Overflow status `413`** ("Too many items requested."): returned when a batch call exceeds that method's `batchCallLimits` entry (check via `api-limits`). NOT specially handled on **writes** — surfaces as a generic error and exits, so split large `keyword-create-batch` / `negative-add-batch` payloads yourself (typically ≤100 items for create/update/remove). **Reads are safe since v1.9.0** — listings and reports page themselves (see the paging note above; report/list cap is 5000 per call).
- **Recommended account entity caps** (Sklik docs — exceeding causes account slowdown and can break bulk ops/imports/API): ≤250 campaigns, ≤250k keywords, ≤4000 negatives per group, ≤100 ads per group, ≤1000 groups per campaign, ≤1000 targeting entries per group. Batch ops are **all-or-nothing** (any item fails → whole batch rolled back). The API's `*.check` methods validate payloads cheaply; the CLI uses `ads.check` internally in `ad-replace` but doesn't expose check commands.
- **Other status codes** (returned by any method): `200` OK, `206` partial OK (warnings in `diagnostics`), `301` user is serviced, `400` bad arguments, `401` invalid session (CLI re-auths once), `403` access denied, `404` not found, `406` bad attribute values, `409` conflict, `500` server error.

## Fénix API (Seznam Nákupy + Sklik campaigns) — a second, separate API

`sklik/fenix.py` + `sklik/commands/nakupy.py` (CLI: `feed-status`, `feed-diagnostics`, `nakupy-campaigns`, `nakupy-stats`, `shop-items`) + `sklik/commands/fenix_sklik.py` (CLI: the `fenix-*` commands, see the subsection below). Everything here is checked against the OpenAPI spec at `https://api.sklik.cz/v1/openapi.json` (title "API Fenix"): first at version 1.26.1 (read 2026-09-07), re-checked at **1.30.0** (read 2026-10-02, changelog at `/v1/changelog.json`); the update commands of v1.12.0 against **1.34.0** (read 2026-10-22). Items marked *(observed)* come from live use by the contributor and are not in the spec; *(live 2026-10-02)* marks what a second contributor confirmed against a live account for v1.11.0; items marked *(spec only)* have never been run against a live account.

**What 1.26.1 → 1.30.0 changed for the Nákupy commands: nothing in the requests.** Every request the five commands send still validates against the 1.30.0 spec (method, path, query names/types/enums, body). The additions are optional (`scope` on `/user/token`, `conversionIds` in the statistics body, `id` on a feed, `PATCH /nakupy/feeds/{feedId}`, `GET /nakupy/favourites/`). The gaps found were on the client side — see the rate-limit and feed notes below.

- **Base URL is `https://api.sklik.cz/v1`** — NOT `/fenix/v1` (that path serves only the docs UI; the spec's `servers` entry is `/v1`). REST/JSON, not JSON-RPC.
- **Auth**: a long-lived **refresh token** (from the Sklik web UI) is POSTed **form-urlencoded** to `/user/token` with `grant_type=refresh_token` + `refresh_token=…` → `{access_token, expires_in}` (~3600 s). The CLI caches it in `.fenix_cache_<account>.json` (git-ignored), refreshed `_TOKEN_SLACK`=120 s early. The DRAK token is not a Fénix token.
- **`--user-id` binds at token-mint time, not per call**: the token request takes an optional `user_id` for a managed account you've been granted access to (403 otherwise). Each managed account therefore gets its own cache slot in the same file.
- **`premiseId` (SHOP id) is required on every `/nakupy/*` call** — `--premise-id` or `SKLIK_FENIX_PREMISE` / `_<NAME>`. It is not a campaign ID.
- **Money units are mixed, and the spec is wrong about one of them.** `maxCpcSearch`, `minCpc` and `productDetailInfo.maxCpc` are plain CZK floats (documented as CZK, examples `1.28`/`42.38`), as are the report money columns — **do not** run those through `_format_money` / `_convert_stats_to_czk`. But `CampaignResponse.budget.dayBudget` is **haléře**, together with its sibling `exhaustedDayBudget`. The spec says CZK there (`Budget-Output`: "Daily budget for the campaigns in CZK", example `5000`) and contradicts itself two schemas later (`Budget-Input` and `BudgetResponse`: "in hellers"). *(observed 2026-09, ArkAngelMichael)* the same campaign read at the same moment gives Fénix `budget.dayBudget = 25000` and DRAK `dayBudget = 25000 haléře = 250 Kč` — identical raw integers, so this endpoint hands DRAK's own value straight through. The CLI divides by 100 in the human output; `--json` passes the raw Fénix payload through untouched.
- **`GET /nakupy/campaigns/`** returns the bid multipliers DRAK cannot show: `websites[]` (`webType`: `seznam`|`partner`|`zbozi`), `devices[]` (`deviceType`: `desktop`|`phone`|`tablet`|`multimedia`), `products[]` (`productType`: `detail`|`offer`). **`maxCpcMultiplier` is a SIGNED PERCENTAGE MODIFIER despite its name — the same convention as DRAK's `devicesPriceRatio` (0 = no change, `+20` = +20 %, `-100` = placement off), so values copy across unconverted.** The spec calls it a "multiplier in percent" with examples `120`/`150`/`200`, but *(observed 2026-09, ArkAngelMichael)* live values are small signed deltas (`seznam +10`, `zbozi -25`, `tablet -50`, `multimedia -100`) that match DRAK's `devicesPriceRatio` for the same campaign 1:1 — and a multiplier can never be `-100`. **Only placements with a modifier actually set are returned** (the spec's own wording: "Websites for which CPC multipliers are set"), so an untouched device is missing from the array rather than present as `100` — never test for a neutral value, test for absence. Only device modifiers are writable, and only via DRAK (`campaign-update --device-bids`); web and auction-type ones have no write endpoint in either API. `zboziBiddingType` says where the CPC comes from: `sklik` (the Sklik campaign), `zbozi` (Centrum prodejce) or `feed` (the feed's `MAX_CPC_SEARCH` tag).
- **`GET /nakupy/diagnostics/item`** is an aggregate only (`total`, `ok`, `error`, `notVisible`, `canBeImproved`, `withoutCategory`, `assignableToCategory` + `*Percentage`, all integers). Serving is blocked only by `error` and `notVisible`; `canBeImproved` means missing optional enrichment.
- **Statistics are async**: `POST /nakupy/statistics/{aggregated,category,item}?premiseId=…` with `{from,to,format:["json"],splitStats?,granularity}` (RFC-3339 datetimes) answers **202** with `{id}`. The data is then read from the **shared** `GET /sklik/reports/{id}?format=json`, which returns `{stats:[…], sums:{…}}`. *(observed)* while the report is still being generated that endpoint answers **425 Too Early** — 425 is not in the spec, so the CLI treats only 425/429 as "keep waiting" and any other non-200 as a real failure. `splitStats`: `deviceType`, `webType`, `productType`, `conversionId` (the last one only for periods from 2026-01-01). `granularity`: `none` (default) / `daily` / `weekly` / `monthly` / `quarterly` / `yearly` — note `none`, not DRAK's `total`.
- **Report rows carry no unit hints for their ratios.** `ctr`, `conversionRatio` and `pno` are documented only as "ratio", with no statement of fraction vs. percent. The CLI therefore **derives** CTR and PNO from the raw counters for human output and passes the API's own columns through untouched in `--json` — a wrong guess here is exactly the 100× bug that hit `ctr` (≤1.7.x) and `conversionValue` (≤1.7.1) on the DRAK side.
- **`GET /nakupy/shop-items/` pages with an OPAQUE CURSOR**, not offsets: `meta.offset` from one response is passed as `offset` to the next and comes back null on the last page; `meta.totalCount` is only sent on the initial cursor-less request. Per-request `limit` caps depend on the detail level: **3000** plain, **300** with `loadSearchInfo`, **50** with `loadProductDetail` (exceeding it is a 422). `itemId` takes ≤100 IDs, ≤50 with `loadProductDetail`. `loadProductDetail=true` adds `product.productDetailInfo` (`fromCheapestPosition`, `topPosition`, `maxCpc` = CPC needed for the TOP position, desktop) but is slow. The CLI shows the first page by default and says so on stderr; `--all` walks the cursor to the end. The `paired` filter is also applied client-side on the per-item `product` field, which is what pairing actually is.
- **`GET /nakupy/feeds/`**: each feed carries an `id` (since 1.27.0; it is the `feedId` of `PATCH /nakupy/feeds/{feedId}`, which the CLI does not wrap). `maxFeedDownloadsPerDay` is `1` / `4` / `16` or **`null` = "downloaded as often as possible"** — null is a value, not a missing one (`feed-status` printed it as `None` until v1.11.0).
- **Rate limits are published in the spec** (the earlier note here said they were not): a default of **5 requests/second across all endpoints**, a `429 Too Many Requests` with a **`Retry-After`** header when exceeded, and `RateLimit-Policy` / `RateLimit` headers on every response (IETF draft-ietf-httpapi-ratelimit-headers-09). There is still no runtime query like DRAK's `api.limits`. Several Nákupy endpoints carry a tighter limit of their own in the spec's `x-rate-limit` extension: **`GET /nakupy/shop-items/` 1 per second**, `GET /nakupy/feeds/` and `GET /nakupy/diagnostics/item` **2 per minute**, `POST /nakupy/statistics/*` 5 per 30 s; the `/sklik/*` and `/user/*` endpoints have none. `/user/token` is "rate-limited" without a number — mint once and reuse (the CLI caches the token for its whole hour).
- **How the CLI paces itself** (`sklik/fenix.py`, independent of the DRAK budget in `api.py`): `_MIN_INTERVAL`=0.6 s between calls, **1.1 s for `/nakupy/shop-items/`** (until v1.11.0 `shop-items --all` paged at 0.6 s — faster than that endpoint's 1 req/s — and leaned on 429 retries). On a 429 it **waits exactly what `Retry-After` says** (seconds or an HTTP-date), falls back to a linear 3/6/9 s back-off if the header is missing, gives up after 3 retries, and refuses outright when the server asks for more than `_RETRY_AFTER_MAX`=120 s. The pacing is per process: the 2-per-minute endpoints can still answer 429 when a command is run three times in a minute — that is what the `Retry-After` wait is for. The CLI does not read the `RateLimit` headers.
- **Report readiness has a documented check the CLI does not use**: `GET /sklik/reports/?id=<id>` lists the report with `status` ∈ `new` / `processing` / `finished` / `maxRowError` / `error`. `poll_report()` instead polls the report body and relies on the *(observed)* 425; a report that ends in `error` / `maxRowError` therefore shows up as a timeout rather than a named failure.

### Sklik campaigns via Fénix (`fenix-*`) — reads verified live, writes mostly *(spec only)*

`sklik/commands/fenix_sklik.py`, added in v1.11.0 against spec 1.30.0. Fénix does not replace DRAK: it has **no endpoints for positive keywords, keyword suggestions or search-query reports**. Updating a campaign, group or ad is a `PATCH`, and so is removing/restoring one (`{"deleted": true|false}`). Since v1.12.0 the CLI wraps the campaign and ad updates (`fenix-campaign-update`, `fenix-ad-update`); group updates and delete/restore are still unwrapped.

**Updates (spec 1.34.0; the request shapes below were sent live 2026-10-22 by a one-off script, the CLI commands themselves are mock-tested only):**

- **The body must carry the entity's `type`.** `PATCH /sklik/campaigns/{id}/` is a `oneOf` keyed on `type` (`fulltext`, `context`, `product`, `simple`, `smart`, `video`, `zbozi`, `social`, `audio`); the type cannot be changed. `PATCH …/ads/{adId}/` is a `oneOf` without a discriminator, told apart by the required `type` const (`eta`, `smart`, `banner`, `combined`, `branding`, `dynamic_banner`). The CLI looks the type up unless `--type` is given.
- **Single-entity reads do not exist**; a campaign is read through the listing. *(live 2026-10-22)* the filter is **`ids` as a list** — the spec names it `id`, but the server validates `ids` ("query.ids: Input should be a valid list" for a scalar) and filters by it.
- **Campaign fields** (all optional, all nullable): `name`, `status`, `budget.dayBudget` (haléře), `totalBudget` (haléře, null = no limit), `startDate`, `endDate`, `capping`, `excludedUrls` (URI strings, replaces the list), `regions`, `devices`, `schedule`, `adSelection`, `totalClicks`, `paymentMethod` (context only). `simple` campaigns have no `capping`.
- **`capping`** (new in 1.34.0, also on groups): `maxImpressions` (int), `maxImpressionsPeriod` (`daily` / `weekly` / `monthly` / `whole`), `minDelay` (int), `minDelayPeriod` (`minute` / `hour`). In a listing's `a` only the dotted fields work — a bare `capping` is a 422. *(live 2026-10-22)* `{"maxImpressions": 3, "maxImpressionsPeriod": "daily"}` on a `context` campaign reads back the same. This is the web UI's campaign-level cap that DRAK cannot see.
- **Dates**: the spec types `startDate` / `endDate` as `date-time` (for ads: "time part is ignored"). *(live 2026-10-22)* a bare `YYYY-MM-DD` is accepted and stored as local midnight (`2026-11-10T00:00:00+01:00`). Whether the end date itself is still a serving day is not documented.
- **Ads**: every type takes `status`, `startDate`, `endDate`, `schedule`, `sensitivity`; `banner` and `branding` also `name`. A change made in place answers **204**; a change to an immutable creative field makes the API delete the ad and create a successor, answering **200 with the new `id`** — `fenix-ad-update` offers no creative fields, but reports such a replacement under `replaced`. *(live 2026-10-22)* `{"type": "banner", "endDate": "2026-11-04"}` on 126 banners: all in place.
- **Not in either API** (spec 1.34.0, DRAK docs read 2026-10-22): a switch to exclude disinformation websites (only own lists via `excludedUrls` / DRAK placements), and choosing which conversions count for a campaign (`/sklik/event-measurement/conversions/` has no campaign field; `conversionIds` on a campaign is a stats split only).

Two things the live run settled beyond single fields: **entity IDs are identical in both APIs** (a campaign/group created through DRAK is addressed by the same ID in Fénix), and **campaign-level negatives written through DRAK are readable through Fénix**. Everything below without a *(live 2026-10-02)* mark is still the spec's word, and the 1.10.1 lesson (the spec was wrong about two Nákupy fields) applies to it.

- **No `premiseId`** on `/user/*` and `/sklik/*`. Same token as the Nákupy commands; each endpoint names the scopes it needs (`campaign`, `campaign_new`, `group_add`, `ad_add`, `keyword`, `keyword_edit`, …). A refresh token is created with an access level `r` / `rw` / `rwa`, and a linked account's own access level caps it further — a write with a read-only token is a 403. `GET /user/me` (`fenix-me`) returns the scopes actually granted, plus `actor` when the token acts on a managed account.
- **Listings return only what you ask for**: the `a` query parameter (repeated: `a=id&a=name`) names the attributes, nested ones dotted (`budget.dayBudget`). It is optional on campaigns / groups / ads / linked accounts — **the spec does not say what comes back when it is omitted** — and *required* on the negative-keyword listings. The CLI always sends an explicit list.
- **Paging is plain `offset` / `limit` (max 1000), with no total count and no cursor** — the response is just `{"items": […]}`. So, as with DRAK's `*.list`, the only complete read is walking offsets until a short page (`fenix.fetch_all_offset()`). The CLI sends `order=id:ASC` where the endpoint has an `order` parameter so the pages are stable; the negative-keyword listings have none. This is a different mechanism from `/nakupy/shop-items/` (opaque cursor in `meta.offset`).
- **Filters are query parameters** (`status`, `isDeleted`, `type`, `id`, …) and are documented as server-side. The live run did not isolate whether the server applies them (the CLI filters again locally, so the output looks the same either way), so the CLI keeps re-applying `status` and `isDeleted` client-side — DRAK documents filters it then ignores. Listings exclude deleted entities (`isDeleted=false`).
- **Status enum is `active` / `suspend`** for campaigns, groups and ads (`Status`) — `suspend` is the paused value *(live 2026-10-02: a paused campaign reads `status: suspend`)*. (The Nákupy campaign listing uses a different, richer enum with `suspended`.) **`fenix-campaign-create` sends `status: suspend` unless `--status active` is passed**; the spec gives campaigns no documented default. Groups default to `active` per the spec, ads have no documented default — the CLI sends `status` for those only when the flag is given.
- **`dryRun=true`** (query parameter) exists on exactly six operations: create and update of campaigns, groups and ads — "only validates … without persisting any changes". The CLI maps `--dry-run` to it on the three creates. **The spec does not describe what a dry run returns** (the same response schema as a real create, whose items require an `id`); the CLI treats any 2xx as "valid" and passes the body through under `response`. *(live 2026-10-02, campaign create only)* a valid payload answers 2xx with `{"items": []}` and creates nothing; an invalid one (`dayBudget` 0) answers 422 with `loc: ["budget.dayBudget"]`, `msg: "Invalid field value"` — note that `loc` holds a single dotted string with no leading `body`, not one array element per path segment. The group and ad dry runs were not tried.
- **The negative-keyword endpoints have NO `dryRun`.** Sending the parameter anyway could be silently ignored and the write performed, so `--dry-run` on `fenix-negative-add` / `fenix-negative-remove` sends **nothing** and only prints the request (`"dryRun": "local", "validated": false` in `--json`).
- **Create bodies are single objects, not arrays** (DRAK takes arrays): campaign `{type, name, budget: {dayBudget}, status, adSelection?}` → `{"items": [{"id"}]}`; group `{name, cpc?, cpm?, status?}`; ETA ad `{type: "eta", headline1, headline2, description, finalUrl, headline3?, description2?, path1?, path2?, mobileFinalUrl?, trackingTemplate?, status?}` (limits 30 / 30 / 30 / 90 / 90 / 15 / 15 chars, URLs ≤ 1024; `path2` requires `path1`). The spec requires only `name` on a group; the CLI insists on `--cpc` or `--cpm`, because the bid a group gets without one is not documented. The other ad types (`smart`, `banner`, `combined`, `branding`, `dynamic_banner`) are not wrapped — most of them reference images uploaded through `/sklik/images/` first; nor are `/sklik/event-measurement/*` and `/sklik/suggest/ad`.
- **Money, field by field, as the spec words it** — and the spec is not consistent with itself across the two halves of the API:
  - **haléře**: campaign `budget.dayBudget` ("in hellers (100 hellers = 1 CZK)" on create, "Daily budget limit in hellers" on read; *live 2026-10-02*: 30 Kč reads `3000`), `exhaustedDayBudget`, `totalBudget`, group `cpc` / `cpm` ("Max CPC in hellers"; *live 2026-10-02* for `cpc`: 3 Kč reads `300`), and every statistics money column of the `/sklik/*` listings (`totalMoney`, `avgCpc`, … and — unlike the DRAK report column — `conversionValue` too). The same budget object in the Nákupy listing (`Budget-Output`) is worded "in CZK" and was shown live to be haléře, so the `/sklik/*` wording is at least consistent with reality there.
  - **CZK**: `credit` / `creditWithVat` of `GET /user/me/credit` (examples `500000` / `605000`, i.e. 21 % VAT; *live 2026-10-02*: `credit` equals what DRAK's `credit` command prints in Kč).
  - **not stated**: `agencyLimit` of the same endpoint (agency clients get it instead of a credit) — "Limit assigned by agency", an integer with no unit. The CLI prints it raw.
  - **ambiguous on purpose not shown**: `devices.maxCpcMultiplier` is worded "Maximum CPC multiplier for the device in percent", exactly like the Nákupy field that turned out to be a signed modifier. `fenix-campaigns` does not request it rather than guess.
  The CLI converts CZK → haléře on `--day-budget` / `--cpc` / `--cpm` and haléře → Kč in the human output; **`--json` passes the raw payload through (haléře)**, the same rule as the Nákupy commands.
- **Negative keywords** (`/sklik/campaigns/{id}/negative-keywords/` and `/sklik/campaigns/{id}/groups/{id}/negative-keywords/`, since 1.20.0): `GET` lists (`a` required: `name`, `matchType`), `POST` adds (201, no body), `PUT` **replaces the whole set** (204; not wrapped), `POST …/negative-keywords/delete` deletes (204) — "permanently", and a delete is a `POST` with a body, not a `DELETE`. **There are no IDs**: an item is `{name, matchType}` in every direction. `matchType` ∈ `negative` / `negativePhrase` / `negativeExact`; that plain `negative` is the broad match (DRAK: `negativeBroad`) is not in the spec, which only calls it "Negative keyword Match Type" — *(live 2026-10-02)* negatives written through DRAK as `negativeBroad` read back as `matchType: negative`. The CLI accepts `negativeBroad` and sends `negative`. **The campaign-level `GET` is what the CLI's DRAK commands cannot do** (`keywords.negative.list` returns group-level only) — *(live 2026-10-02)* it listed 33 campaign-level negatives written through DRAK. (DRAK's docs also list `keywords.campaign.negative.createReport` / `readReport`; the CLI does not use them and they were not tried, so "write-only in DRAK" is proven only for the `*.list` route.) 1.21.2 removed `negativeWords` from the campaign create/update bodies, so these endpoints are the only Fénix way to write them.
- **Errors** are `{"detail": [{"loc": […], "msg": "…", "type": "…"}]}` (422 validation, 403, 404; the 422 shape was seen live, see `dryRun` above). The CLI puts `loc: msg` into the error message and keeps the full body under `error.detail` in `--json`. A failed `--dry-run` is exactly this: a 422 and a non-zero exit.
- **Write responses can be body-less**: negative add → 201, negative delete / replace and the `PATCH` updates → 204. `fenix.call()` returns `{}` for those.
- **Open, DRAK side** *(observed 2026-10-02, not explained)*: for the same groups where Fénix returns `cpc: 300`, DRAK's `groups --json` printed `maxCpc: null`. The CLI asks `groups.list` for the `maxCpc` column, which is the only CPC column that method documents ("maximum cpc for group's targeting"; there is no `cpc` column, while `groups.create` takes the bid as `cpc`, "Group default maximal cost per click"). So the column name matches the docs and the cause is not established — either `maxCpc` is not the group's own default bid, or the API omits it in this case. Until that is cleared up, read a group's bid through `fenix-groups`.
